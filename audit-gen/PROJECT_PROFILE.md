# Project Profile — CricBudz (IPL Fantasy Arena)

> Generated by exploring the repository directly (package.json, config files,
> source under `src/`, `firestore.rules`, `public/`). Treat everything below
> as a description of what exists in the code, not an endorsement of it.

## 1. What this project is

CricBudz is a **fantasy cricket web app for the IPL (Indian Premier League)**,
built for a small private friend group (explicitly not a public product —
see `CLAUDE.md`/`PROGRESS.md` in the repo root, which state SEO/scale/
multi-tenant concerns are out of scope by design decision).

Core gameplay loop:
- For each IPL match, a signed-in user drafts a **"trio"**: exactly 3 players
  drawn from the two playing teams.
- The user tags exactly one of the three as **MVP**, worth 2x points
  (`MVP_MULTIPLIER = 2` in `src/lib/scoringRules.ts`).
- The trio must include players from **both** playing franchises — an
  all-one-team trio is rejected (`checkDualFranchiseViolation` /
  `validateSquad` in `src/lib/draftRules.ts`).
- Squads lock 30 minutes before match start ("toss") and can't be edited
  after (`SQUAD_LOCK_WINDOW_MS` in `src/lib/utils.ts`, enforced both in the
  UI and in `firestore.rules`).
- After a match, an admin manually triggers scoring
  (`POST /api/finalize-match`), which fetches the real Cricbuzz scorecard,
  computes points per player from real match stats, and writes
  `totalPoints` onto every submitted squad.
- A **Monday–Sunday weekly leaderboard** (`/leaderboard`) ranks users by
  total trio points for the week, computed live on every page load (no
  rollup job or separate leaderboard collection).

Secondary features:
- **"Squad Room"**: view other users' submitted trios for a match, subject
  to an admin-controlled **visibility toggle** that can hide picks from
  other users until toss on a chosen day (anti-copying feature).
- **Admin panel** (`/admin`): manual data sync from Cricbuzz, match
  finalization/scoring, a dev date-override tool, the visibility toggle,
  user management (grant/revoke admin via Firebase custom claims), and a
  read-only JSON data backup export.
- **Rules page** (`/rules`): human-readable scoring rules, generated from
  the same constants the scoring engine uses, so they can't drift apart.

## 2. Tech stack

**Language & framework**
- TypeScript (strict mode, `tsconfig.json`), Next.js 15.5 (**App Router**),
  React 18.3, React DOM 18.3.
- Node.js server runtime for Next.js API routes (`src/app/api/**/route.ts`).

**Styling / UI**
- Tailwind CSS v4 (`@tailwindcss/postcss`, CSS-first `@theme` config in
  `src/app/globals.css` — no `tailwind.config.js`).
- `clsx` + `tailwind-merge` composed into a `cn()` helper
  (`src/lib/utils.ts`) — with a custom extension teaching `tailwind-merge`
  about two project-specific font-size tokens (`text-meta`, `text-micro`)
  that stock tailwind-merge would otherwise mis-classify as color utilities
  and silently drop.
- `lucide-react` for icons, `sonner` for toast notifications, `motion`
  (Framer Motion successor) for animation.
- Google Fonts via `next/font/google`: Inter (sans/body), Space Grotesk
  (display/headings), JetBrains Mono (mono).
- Manual dark/light theming via a `.dark` class toggled by `ThemeContext`
  (not solely OS `prefers-color-scheme`), with a no-flash inline script in
  `layout.tsx` that applies the stored theme before hydration.

**Backend / data**
- **Firebase** as the entire backend:
  - **Firebase Auth** (Google sign-in, popup with redirect fallback) —
    `src/context/AuthContext.tsx`.
  - **Firestore** (a *named* database, not `(default)` — `FIREBASE_DATABASE_ID`)
    for all persistent data: `matches`, `players`, `userSquads`, `settings`,
    `auditLog`.
  - Two separate SDK paths into the same Firestore:
    - **Client SDK** (`src/lib/firebase.ts`, `firebase` npm package) — used
      by all `'use client'` pages and `src/services/dataService.ts` for
      reads and user-squad writes. Uses `initializeFirestore` with
      `persistentLocalCache`/`persistentMultipleTabManager` (IndexedDB
      offline cache) and `experimentalForceLongPolling: true`. Can connect
      to the Firebase Emulator Suite when
      `NEXT_PUBLIC_USE_FIREBASE_EMULATOR=true` (E2E tests only).
    - **Admin SDK** (`src/lib/firebase-admin.ts`, `firebase-admin` npm
      package, server-only) — used by admin API routes
      (`/api/sync`, `/api/finalize-match`, `/api/admin/users`,
      `/api/admin/backup`). Authenticates via a service-account credential
      built from `FIREBASE_PROJECT_ID` / `FIREBASE_CLIENT_EMAIL` /
      `FIREBASE_PRIVATE_KEY` env vars, and does **not** auto-fall-back to
      the client's named database — `FIREBASE_DATABASE_ID` must be set
      explicitly for it too.
  - **Firestore Security Rules** (`firestore.rules`) — default-deny at the
    root; per-collection rules layered on top (see §4).
- **RapidAPI's Cricbuzz-Cricket endpoint** (`src/lib/rapidapi.ts`) is the
  sole external sports-data source: match fixtures, team squads/players,
  and post-match scorecards. Requires `RAPIDAPI_KEY` /
  `RAPIDAPI_HOST=cricbuzz-cricket.p.rapidapi.com`.
- **Zod** (`zod` v4) for runtime schema validation of the Cricbuzz scorecard
  response before it's trusted by the scoring engine
  (`ScorecardResponseSchema` in `src/lib/scoring.ts`, `.passthrough()` so
  unknown new fields don't break validation — only fields the code actually
  depends on are checked).

**Build & tooling**
- `next build` / `next dev` / `next start`, ESLint (`eslint-config-next`).
- **Vitest** (+ `@testing-library/react`, `jsdom`) for unit/component tests,
  colocated as `*.test.ts(x)` next to source.
- **Playwright** for E2E tests (`e2e/`), driven against a real **Firebase
  Emulator Suite** (Auth + Firestore) via a test-only
  `window.__testSignInWithCustomToken()` hook gated on
  `NEXT_PUBLIC_USE_FIREBASE_EMULATOR=true`.
- **`@firebase/rules-unit-testing`** for dedicated Firestore rules tests
  (`rules-tests/`), run against a throwaway emulator instance spun up by
  `firebase emulators:exec`.
- Deployed on **Vercel** (`.vercel/` present; live at
  `https://ipl-fantasy-arena.vercel.app` per CLAUDE.md).
- Firebase CLI config present (`firebase.json`, `.firebaserc`,
  `firestore.indexes.json`) for deploying rules/indexes and running local
  emulators.

**Notable absences** (intentional, per project docs): no ORM/SQL database —
Firestore only; no state-management library (Context API + Firestore
snapshots only); no server framework beyond Next.js route handlers; no
component library dependency (a small hand-rolled `src/components/ui/`
kit instead); no image CDN beyond Next.js's built-in `next/image` with
allow-listed remote hosts (Cricbuzz's CDN, `picsum.photos` for
placeholders).

## 3. Output surface(s)

**Single surface: a responsive web app**, explicitly designed **phone-first**
but usable on desktop.

- **Progressive Web App (PWA)**: `public/manifest.json` declares
  `display: "standalone"`, `orientation: "portrait"`, `start_url:
  "/dashboard"`, and app icons (192/512/maskable). This makes it
  installable to a phone home screen and run in an OS-chrome-free window,
  but there is **no service worker** in the repo (no offline-first caching
  of the app shell) — the "PWA-ness" here is limited to the installable
  manifest + icons, not full offline support.
- Mobile UI uses a **bottom tab bar** (`BottomNav.tsx`); desktop uses
  `TopBar.tsx`'s inline nav links instead (`NavigationWrapper.tsx` switches
  between them, and hides all chrome on `/`, when logged out, and on the
  match-draft page which has its own custom chrome).
- No native mobile app (no React Native/Capacitor/Cordova wrapper found),
  no native desktop app (no Electron/Tauri), no standalone CLI tool
  distributed to end users (the `scripts/` directory holds internal
  maintenance scripts run via `node`, not a packaged CLI).
- The Next.js app also serves as the **backend**: API routes under
  `src/app/api/**` are the only server-side logic (no separate backend
  service/repo).

## 4. Architecture (high level)

```
┌───────────────────────────────────────────────────────────────────┐
│ Browser (React 18 client components)                               │
│  Contexts: AuthContext · DevContext · ThemeContext                  │
│  Pages: / , /dashboard , /matches , /matches/[id] , /leaderboard ,  │
│         /rules , /admin                                             │
│  UI kit: Button, Card, Badge, Sheet (modal), Skeleton, ErrorState    │
└───────────────┬───────────────────────────────┬────────────────────┘
                │ Firebase client SDK            │ fetch()
                │ (reads + user-squad writes)    │ (Bearer ID token)
                ▼                                ▼
   ┌─────────────────────────┐      ┌─────────────────────────────────┐
   │ Firestore                │      │ Next.js API routes (server)      │
   │  matches, players         │◄────│  /api/sync           (admin)      │
   │  userSquads, settings,    │Admin│  /api/finalize-match (admin)      │
   │  auditLog                 │ SDK │  /api/admin/users    (admin)      │
   │                           │     │  /api/admin/backup   (admin)      │
   │  firestore.rules enforces │     │  /api/leaderboard    (auth'd)     │
   │  ownership/toss-lock/     │     │  /api/matches/[id]/squads (auth'd)│
   │  visibility at the doc    │     └───────────────┬───────────────────┘
   │  level                    │                     │
   └─────────────▲─────────────┘                     │ server-side fetch
                 │ populated only by                 ▼
                 │ /api/sync (Admin SDK)   ┌────────────────────────┐
                 └─────────────────────────│ RapidAPI (Cricbuzz)     │
                                            │ fixtures/players/scores │
                                            └────────────────────────┘
```

**Data flow / ETL.** `GET /api/sync` is the *only* path that populates
`matches` and `players` in Firestore — it calls Cricbuzz via
`src/lib/rapidapi.ts`, keyed off `CRICKET_CONFIG.IPL_SERIES_ID` /
`IPL_SEASON` (`src/config/cricket.ts`, currently series `'9241'`, season
`'2026'` — this is the single place to roll over for a new IPL season).
Player `price` is currently **randomized** (`8 + Math.random() * 3` per the
codebase's own comments) — there is no real pricing model yet. Sync
collects any team whose player-list response comes back missing/reshaped
into a `teamsWithNoPlayers` warning rather than silently skipping it.
`seriesId` is coerced to a string at write time because Cricbuzz returns it
as a number while `IPL_SERIES_ID` is a string, and match-day filtering
elsewhere in the app does a strict `==` comparison against it.

**Auth model.** Every admin-only API route funnels through a single
`requireAdmin(req)` helper (`src/lib/adminAuth.ts`) that verifies a Bearer
Firebase ID token and checks the `admin` custom claim; a parallel
`requireAuth(req)` does the same token check without the claim requirement
for routes any signed-in user can call. Admin status is a Firebase Auth
**custom claim**, checked server-side on every admin route — not just
hidden client-side.

**Firestore security rules** (`firestore.rules`) default-deny everything,
then layer on:
- `userSquads/{squadId}`: owner-only write, shape-validated (exactly 3
  players + MVP-in-players + doc ID literally `{userId}_{matchId}`),
  cross-checked against the real `matches` doc so a client can't spoof
  `matchTimestamp`/`matchDay`, and blocked entirely once 30 minutes before
  match start has passed. Reads are owner-always, or gated by the
  visibility-toggle/toss logic below for other users.
- `settings/{settingId}`: any signed-in user can read, only admins can
  write (backs the visibility toggle).
- `matches/{matchId}` / `players/{playerId}`: world-readable, write always
  denied from clients (writes only ever happen via the Admin SDK, which
  bypasses rules).
- `auditLog/{logId}`: admin-read, client-write always denied.

**Submission visibility toggle** is deliberately enforced in *three*
places, not just rules: `firestore.rules` handles the single-document
"is this user's own squad" case, but Firestore rules cannot structurally
prove correctness for the multi-document `list` queries the leaderboard's
match-day range query and Squad Room's cross-user query need — those get
rejected outright by the rules engine regardless of whether the data
should be visible. So `GET /api/leaderboard` and
`GET /api/matches/[matchId]/squads` (both `requireAuth`, using the Admin
SDK, which bypasses rules) **reimplement the same visibility policy in
application code** as a deliberate workaround, confirmed empirically via
the `rules-tests/` suite.

**Scoring engine** (`src/lib/scoring.ts` + `src/lib/scoringRules.ts`).
`POST /api/finalize-match` fetches the real Cricbuzz scorecard, validates
its shape against `ScorecardResponseSchema` (Zod, `.passthrough()`) via
`validateScorecardResponse()` — if a field the engine depends on is
missing or retyped, this throws a specific, named error and the route
returns HTTP 502, deliberately refusing to compute (rather than risk
silently wrong) scores. Known real-world data gaps baked into the design:
Direct Hit is folded into Runout (Cricbuzz doesn't distinguish them), Man
of the Match is entered manually by the admin (not exposed by the API),
fielding-credit name-matching is best-effort text parsing with a
surname-based fallback (Cricbuzz's data has been observed spelling the
same player two different ways within one response), and the Dot Ball
rule may rarely fire since bowler `dots` data observed during development
was consistently `0`.

**"Today"/date canonicalization.** `getMatchDayIST()`
(`src/lib/utils.ts`) is the single function every "what day is this" /
"is this today" comparison in the app goes through, anchored to India
Standard Time (the league's real timezone) rather than UTC or the
viewer's device timezone — used by the dashboard's "Today's Arena",
fixtures' auto-scroll target, the visibility toggle's match-day check, and
the leaderboard's Monday–Sunday week math
(`src/lib/leaderboard.ts`). One deliberate exception:
`userSquads.matchDay` is still written as a **UTC** slice of
`matchTimestamp` (not IST) because `firestore.rules`' 
`matchesSourceOfTruth()` enforces it as a literal regex prefix and rules
has no timezone-aware date function — the code's own comments say this is
only safe because real IPL matches always start at 10:00/14:00 UTC, so the
UTC-slice day and the IST day coincide for actual match data.

**Trio draft rules** live in `src/lib/draftRules.ts` (pure functions, unit
tested): exactly 3 players from exactly 2 teams, one MVP, enforced both
client-side (UI) and server-side (`firestore.rules`' `isValidSquadShape`)
before a squad can be saved (`saveUserSquad` in `dataService.ts`, doc ID
`{userId}_{matchId}`). `getMatchTimeStatus()` (`src/lib/utils.ts`) derives
a three-way `open`/`locked`/`completed` state from match date vs. current
time — there's no live ball-by-ball sync, so "completed" is a heuristic
(~4 hours after start), not an observed fact.

**Route structure** (`src/app/`):
- `/` — landing/sign-in.
- `/dashboard` — home for a signed-in user ("Today's Arena", quick links).
- `/matches` — fixture list, auto-scrolls to today's match.
- `/matches/[id]` — the trio-draft "arena" (composed from
  `_components/PlayerCard.tsx`, `SelectedSlots.tsx`,
  `SubmissionControl.tsx`), plus "Squad Room" and the admin
  "Finalize Match" card on the same page.
- `/leaderboard` — live-computed weekly rankings.
- `/rules` — scoring rules copy, generated from `scoringRules.ts`.
- `/admin` — gated by `isAdmin` (client hides it, but every admin API
  route independently re-checks the custom claim server-side): manual
  sync trigger, dev date override (`DevContext`), visibility toggle,
  registered-users management, data backup export.
- `src/app/api/**/route.ts` — the 6 API routes described above.

**Contexts** (`src/context/`, all wrapping the app in `layout.tsx` above
`NavigationWrapper`):
- `AuthContext` — Firebase Auth state, Google sign-in (popup, redirect
  fallback).
- `DevContext` — localStorage-backed date override + `getEffectiveNow()`,
  read by the admin page and several date-sensitive views (lets an admin
  simulate "today" for testing without changing the system clock).
- `ThemeContext` — auto/manual dark-light mode, backed by a `.dark` class
  and localStorage key `ipl_theme_preference`.

### Typography

- **Fonts** (via `next/font/google`, exposed as CSS vars):
  - `--font-sans` = Inter — body text (`font-family: var(--font-sans)` on
    `<body>`).
  - `--font-display` = Space Grotesk — headings/buttons (`.font-display`
    utility class; `Button` uses `font-display font-black uppercase
    tracking-tight`).
  - `--font-mono` = JetBrains Mono — used for numeric/stat displays
    (`.font-mono` utility).
- **Custom font-size tokens** (documented in `globals.css` as "audit item
  #9", a deliberate legibility-floor fix): the app is phone-first with
  small uppercase micro-labels, and informational text had drifted as
  small as 7–10px before this fix.
  - `text-meta` = 12px (`0.75rem`, line-height `1rem`) — the floor for
    informational text users actually read: player roles/prices, status
    lines, dates/times, leaderboard sub-labels, trio-chip surnames.
  - `text-micro` = 11px (`0.6875rem`, line-height `0.875rem`) — reserved
    for purely decorative uppercase micro-labels (stat captions, "Browse
    all", slot labels).
  - `cn()` (`src/lib/utils.ts`) has a documented `tailwind-merge`
    extension registering these two as font-size-group members — without
    it, merging `text-micro` with a color utility like `text-muted` would
    silently drop the size and fall back to the 16px browser default
    (this reportedly broke bottom-nav label sizing once already).

### Spacing / shape

No separate spacing scale is declared beyond Tailwind's defaults — spacing
uses stock Tailwind utilities (`p-`, `gap-`, etc.). Shape/elevation
conventions observed in the UI kit:
- Cards: `rounded-3xl`, `bg-surface`, `border border-border`, `shadow-sm`
  (`src/components/ui/Card.tsx`).
- Buttons: `rounded-2xl`, uppercase display font, `active:scale-[0.97]`
  press feedback, `disabled:opacity-40`; three sizes (`sm` 36px / `md` 44px
  / `lg` 48px tall) and four variants (`primary`, `secondary`, `ghost`,
  `destructive`) — `src/components/ui/Button.tsx`.
- Modals: `Sheet.tsx` — a bottom-sheet-style dialog (`role="dialog"`,
  focus trap, Escape-to-close), documented as fully keyboard-accessible.
- Utility classes: `.no-scrollbar` (hide scrollbars cross-browser),
  `.pt-safe`/`.pb-safe`/`.mb-safe` (iOS safe-area insets for the
  installed-PWA/notch case).

### Component library

Small, hand-rolled, no external UI framework dependency:
`src/components/ui/{Badge,Button,Card,ErrorState,Sheet,Skeleton}.tsx`, plus
app-level chrome components `src/components/{BottomNav,DevOverrideBanner,
NavigationWrapper,ProfileSheet,TopBar}.tsx`. All compose class names
through the shared `cn()` helper for Tailwind-safe merging.
